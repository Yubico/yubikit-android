== FIDO module

The FIDO module enables applications to authenticate WebAuthn credentials on a YubiKey.

The current implementation follows the https://www.w3.org/TR/webauthn-3/[Webauthn Level 3] and https://fidoalliance.org/specs/fido-v2.3-rd-20251023/fido-client-to-authenticator-protocol-v2.3-rd-20251023.html[CTAP 2.3] specifications and can include more properties from newer standard versions.

https://developers.yubico.com/yubikit-android/JavaDoc/fido/latest/[JavaDoc API documentation]

=== Dependency

To add the Fido module, along with the link:../android/[Android] module as a dependencies to your project, add the following to your gradle configuration:

[source,groovy]
----
dependencies {
  implementation 'com.yubico.yubikit:android:(insert version here)'
  implementation 'com.yubico.yubikit:fido:(insert version here)'
}
----

This module depends on the link:../core/[core] module, which will automatically be added as a transitive dependency to your project.

==== Communication with the FIDO Application

To communicate with the Fido application on a YubiKey, use the CtapSession class.
The class provides constructors for Fido or SmartCard connections, as well as a factory method which takes a YubiKeyDevice and will use the best suited connection type available.

The SDK provides a WebAuthn client implementation which communicates with the YubiKey through CTAP1 and CTAP2 and can make new credentials or assert existing credentials.
The client has also functionality for working with the PIN.

Credential operations provided by WebAuthnClient use classes which map to standard Webauthn types and allow easier interoperability with RPs.
For example `PublicKeyCredential.toMap()` returns a standard Java `Map` object which can be serialized to JSON representation:

[source,java]
----
CtapSession session = ...;
WebAuthnClient client = new WebAuthnClient(session);
PublicKeyCredential credential = client.makeCredential(params);
String response = JSONObject(credential.toMap()).toString();
----

==== Legacy U2F extensions: `appid` and `appidExclude`

The client supports the WebAuthn `appid` and `appidExclude` extensions, which let users authenticate with (or avoid re-registering) credentials that were originally created through the legacy FIDO U2F API.

Both extensions require the client to decide whether the _calling application_, identified by its FacetID, is authorized to use the supplied AppID.
Per the https://fidoalliance.org/specs/fido-uaf-v1.1-id-20170202/fido-appid-and-facets-v1.1-id-20170202.html[FIDO AppID and Facets] specification this means fetching the trusted-facets list published at the AppID URL and checking the FacetID against it.

The SDK ships the standardized parts so this works out of the box:

* `TrustedFacetsAppIdVerifier` (in the `fido` module) fetches the trusted-facets JSON over HTTPS, parses it, matches the FacetID, and caches the result. It is the *default* `AppIdFacetVerifier`, so you do not have to implement it.
* `FacetId` (in the `android` module) computes the caller's FacetID from its signing certificate: `FacetId.forSelf(context)` for your own app, or `FacetId.forCallingApp(context, packageName)` when servicing another app's request.

For the common self-relying-party case, setting the FacetID is all that is required:

[source,java]
----
Ctap2Client client = new Ctap2Client(session);

// Enables appid/appidExclude; the default TrustedFacetsAppIdVerifier does the rest.
client.getUserAgentConfiguration().setAppIdFacetId(FacetId.forSelf(context));
----

Advanced integrators (for example a credential provider that must honor same-site /
registrable-domain-suffix rules using a Public Suffix List) can override the verifier:

[source,java]
----
client.getUserAgentConfiguration().setAppIdFacetId(FacetId.forCallingApp(context, callerPackage));
client.getUserAgentConfiguration().setAppIdFacetVerifier((appId, facetId) -> {
  // Your own trusted-facets evaluation (I/O + JSON + PSL/asset-links as needed).
  return isAuthorized(appId, facetId);
});
----

Notes:

* The FacetID is the single opt-in. Until `setAppIdFacetId(...)` is called the extensions stay inert: `appid` is skipped with a warning (it is best-effort — the only consequence is that legacy U2F credentials are not found), while `appidExclude` fails closed with `ClientError.Code.BAD_REQUEST` (silently ignoring it would allow re-registering an excluded credential).
* The verifier is invoked on the same background thread as the credential operation, so a blocking network call is acceptable; do not call it on the main thread.
* The default verifier caches results per AppID for its lifetime and treats a missing document (HTTP 404) as "no trusted facets". A transport error propagates and is not cached, so the ceremony fails rather than silently authorizing.
